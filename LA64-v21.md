## Introduction

There are two names you will see for the same thing:

| Name      | What it is |
|-----------|------------|
| `emex64`  | LA64 |
| `emex64e` | LA64 with the pointer authentication extension (PAC), the toolchain calls that one `la64e` |

The CPU model that currently exists is the `emex64e-2100`.

Some words I use in this file so nobody gets confused, a byte is 8 bit, a word is 16 bit, a double word is 32 bit and a quad word is 64 bit.

## ISA versions
Every version only adds things, nothing was removed since v15.

| Version | What came with it |
|---------|-------------------|
| v15     | The base, everything that is not in one of the rows below. |
| v16     | `rdrnd`, the block memory instructions `movm`, `cpym`, `setm` and `svc`. |
| v17     | The trap model and atomics. |
| v18     | The floating point unit (FPU). |
| v19     | Binary size reduction (`sext`, `cblt`, bit counting, `mulh`, carry arithmetic) and the PAC extension. |
| v20     | The performance update. `rdtime`, `wfe`/`sev`/`pause`, more compare and branch instructions, sign extending loads, more atomics and `tlbi`. |
| v21     | The 32bit arithmetic update. |

The `crisa` control register tells which version a core runs and lets the kernel or firmware select a older one on-demand:

| Bits      | Meaning |
|-----------|---------|
| 15 - 0    | The ISA version that is active right now. This is the only part that can be written. |
| 31 - 16   | The newest ISA version the core supports, `21`. |
| 47 - 32   | The CPU model, `2100`. |
| 48        | Set when the core has the PAC extension. |

Writing a version the core doesn't support (older than v17 or newer than v21) raises a bad instruction exception. The assembler also knows about versions, it refuses to assemble a instruction that is newer than the ISA version you target.

## Instruction coding
The instruction coding is variable, it is not a fixed lenght instruction set, which is a CISC concept. Instructions are coded by the first 8 bit serving as the opcode, followed by operands that are not aligned to a byte boundary. Operands are coded by the first 4 bit serving as the type of operand followed by the operand it self, except it is a offset coding, that means that 2 more operands will follow where the first one is the main operand and the 2nd one is the operand responsible for the offset.

Bits are filled in from the lowest bit of a byte upwards, and everything that is bigger than a byte is little endian. When a instruction is done it gets padded to the next byte boundary, so every instruction starts at a byte address. There is no alignment requirement for instructions other than that.

| Type               | Binary       | Description                |
|--------------------|--------------|----------------------------|
| End                | `0b0000`     | Terminates the instruction, decoder stops decoding |
| Register           | `0b0001`     | 4 bit register identifier of the main register file |
| Immediate (4bit)   | `0b0010`     | 4 bit immediate            |
| Immediate (8bit)   | `0b0011`     | 8 bit immediate            |
| Immediate (16bit)  | `0b0100`     | 16 bit immediate           |
| Immediate (32bit)  | `0b0101`     | 32 bit immediate           |
| Immediate (64bit)  | `0b0110`     | 64 bit immediate           |
| Address (64bit)    | `0b0111`     | 64 bit immediate, with the difference that the decoder aligns to the next byte boundary before it reads it, this was done with the intention for easy address relocation in the linker, it payed off >:3. |
| Register Extended  | `0b1000`     | 4 bit register identifier to the 2nd register file |
| Register Increment | `0b1001`     | 4 bit register identifier, the operand is the value of the register and the decoder increments the register by one after it took the value |
| Register Decrement | `0b1010`     | 4 bit register identifier, the operand is the value of the register and the decoder decrements the register by one after it took the value |
| Offset Add         | `0b1011`     | Two more operands follow, the operand is the first one plus the second one |
| Offset Subtract    | `0b1100`     | Two more operands follow, the operand is the first one minus the second one |
| Register Float     | `0b1101`     | 4 bit register identifier to the floating point register file |

Everything from `0b1110` upwards is a illegal coding and raises a bad instruction exception.

Some rules that come with that:

- Immediates are not sign extended when they are used as a value. `mov r0, 0xFF` gives you 255. The only place where a immediate is signed is a branch target, see "Branch targets".
- A instruction with a fixed amount of operands just ends after the last one. A instruction that got less operands than it can take (the variadic ones and the ones with optional operands) is terminated by the End coding.
- A offset is one operand, the two operands behind the offset coding don't count. A offset inside of a offset is not a thing and raises a bad instruction exception.
- A offset is only math, it does not read memory by it self. `[r1 + 8]` is the value of `r1` plus 8 and what the instruction does with that value is up to the instruction. Thats why `ldq r0, [r1 + 8]` loads from that address and `add r0, [r1 + 8]` just adds that number.
- "Register Increment" and "Register Decrement" only exist for the main register file.
- A instruction can have 16 operands at max, which makes the longest possible instruction 145 bytes.
- In case it is a immediate it gets stored into a immediate cache of the core which then gets used as a operand inside of the operation logic. Offsetted operands are always in the immediate cache. Thats why writing to a immediate does nothing.

A few codings so you see it in action:

| Assembly                      | Bytes                                  |
|-------------------------------|----------------------------------------|
| `nop`                         | `01`                                   |
| `b r5`                        | `26 A1`                                |
| `b 0x1122334455667788`        | `26 07 88 77 66 55 44 33 22 11`        |
| `mov sp, <64 bit address>`    | `02 11 07` and then the 8 address bytes |

In the 2nd one `A1` is the register coding `0b0001` in the low half and `r5` (`0b1010`) in the high half. In the last two `07` is the address coding and the padding to the byte boundary.

### Branch targets
The operand that says where to branch to works like this:

- When it is a 4, 8, 16 or 32 bit immediate it is a signed displacement that gets added to the address of the branch instruction it self, not to the address behind it.
- When it is anything else (a 64 bit immediate, a address, a register, a offset) it is the absolute address to branch to.

So `b` with a 8 bit immediate of `0xFE` branches two bytes back and `b r5` branches to what ever is in `r5`.

## Register Set (RS)
All registers are 64 bit wide.

### Main Register File
Each of these registers are accessible in userspace aswell as in kernelspace. These registers also support the operand codings like "Register Increment" and "Register Decrement."

| Register  | Name                                  | Binary       | Description |
|-----------|---------------------------------------|--------------|-------------|
| `pc`      | **P**rogram **C**ounter               | `0b0000`     | Points to the current address at which the CPU currently is, it increments by the lenght of the instruction when the CPU is done executing the instruction at which PC points to at that time. Reading it as a operand gives you the address of the instruction that reads it. |
| `sp`      | **S**tack **P**ointer                 | `0b0001`     | Points to the current address at which the stack lives, the stack grows downwards on allocation and upwards on deallocation. |
| `fp`      | **F**rame **P**ointer                 | `0b0010`     | Points to the address at which the stack frame of the last function call lives, basically empowering you to branch and link and return back. |
| `cf`      | **C**ontrol **F**lag                  | `0b0011`     | Used by control flow operations like `cmp`, `be` and `bne`. Basically used for if else kind of statements. |
| `fpc`     | **F**loating **P**oint **C**ontrol    | `0b0100`     | Controls the rounding of the FPU and collects its exception flags. |
| `r0` - `r9`      | General Purpose Registers      | `0b0101` - `0b1110`   | Use it for what ever. |
| `rr`      | **R**eturn **R**egister               | `0b1111`    | Unaffected by operations like `blw` and `wret`. Intended to be used as a return value register. |

### Extended Register File
As only 10 general purpose registers is not much we created a extended register file, but the cavet is that it doesn't support direct decode level manipulation like increment and decrementing in place.

| Register  | Name                                  | Binary       | Description |
|-----------|---------------------------------------|--------------|-------------|
| `er0` - `er15` | Extended General Purpose Registers | `0b0000` - `0b1111`   | Use it for what ever. |

### Floating Point Register File
| Register  | Name                                  | Binary       | Description |
|-----------|---------------------------------------|--------------|-------------|
| `fr0` - `fr15` | Floating Point Registers | `0b0000` - `0b1111`   | Hold a double in all 64 bit or a single in the low 32 bit. They can be moved, pushed, loaded and stored like any other register, that just moves the raw bits. |

### Control Register File
Control registers are not operands, they are selected by their number in `cmov`, `cmovb` and `cswp`.

| Register  | Name                                                        | Binary       | Description |
|-----------|-------------------------------------------------------------|--------------|-------------|
| `crel`    | **C**ontrol **R**egister **E**leveation **L**evel           | `0b0000`     | Controls the elevation of the core, the higher the value the more priveleged the core is. |
| `crksp`   | **C**ontrol **R**egister **K**ernel **S**tack **P**ointer   | `0b0001`     | Stores the address of the stack base used when the interrupt controller interrupts the core in the legacy interrupt model. |
| `crexc`   | **C**ontrol **R**egister **E**xception                      | `0b0010`     | Stores exception information. |
| `crvec`   | **C**ontrol **R**egister **V**ector                         | `0b0011`     | Not used anymore. |
| `crptb`   | **C**ontrol **R**egister **P**age **T**able **B**ase        | `0b0100`     | Is treated by the MMU as the 5th level page table entry. |
| `crfpc`   | **C**ontrol **R**egister **F**loating **P**oint **C**ontrol | `0b0101`     | Not used anymore. |
| `crisa`   | **C**ontrol **R**egister **I**SA                            | `0b0110`     | Used to get the ISA version and select older ISA version on-demand if firmware or kernel was intended for running on older ISA. |
| `crstat`  | **C**ontrol **R**egister **Stat**us                         | `0b0111`     | Trap model enable, interrupt enable and the state before the last trap. |
| `crtvec`  | **C**ontrol **R**egister **T**rap **Vec**tor                | `0b1000`     | Address of the trap entry. |
| `crepc`   | **C**ontrol **R**egister **E**xception **PC**               | `0b1001`     | Where `eret` returns to. |
| `crcause` | **C**ontrol **R**egister **Cause**                          | `0b1010`     | What caused the trap. |
| `crtval`  | **C**ontrol **R**egister **T**rap **Val**ue                 | `0b1011`     | Faulting address. |
| `crscratch` | **C**ontrol **R**egister **Scratch**                      | `0b1100`     | Not used by the CPU, needed by trap handlers to have a place to put a register. |
| `criakey` | **C**ontrol **R**egister **I**nstruction **A** **Key**      | `0b1101`     | The key for instruction pointers (PAC). Can be written, never read. |
| `crdakey` | **C**ontrol **R**egister **D**ata **A** **Key**             | `0b1110`     | The key for data pointers (PAC). Can be written, never read. |
| `crpac`   | **C**ontrol **R**egister **PAC**                            | `0b1111`     | Turns pointer authentication on per elevation level. |

Who is allowed to do what:

- Writing any control register needs kernel elevation, otherwise it raises a permission exception.
- `crel`, `crexc` and `crisa` can be read from userspace. All the others need kernel elevation to be read.
- `criakey` and `crdakey` can not be read by anybody, reading them raises a permission exception. A key that can be read is not a key.
- `crvec` and `crfpc` are leftovers, touching them raises a bad instruction exception.

### The control flag
`cf` is a normal register that you can read and write, these are the bits the CPU uses:

| Flag | Value   | Set by |
|------|---------|--------|
| Z    | `0x01`  | `cmp` and `fcmp` when both values were equal, `cas` when it swapped |
| L    | `0x02`  | `cmp` and `fcmp` when the first value was less than the second one |
| G    | `0x04`  | `cmp` and `fcmp` when the first value was greater than the second one |
| U    | `0x08`  | `fcmp` when the values are unordered (one of them is a NaN), then Z, L and G are all clear |
| C    | `0x10`  | `adc` and `sbb`, the carry or borrow |

`cmp` compares signed. ALU operations other than `adc` and `sbb` do not touch `cf`, emex64 has no flags that change behind your back on every addition.

### Elevation levels
| Level           | Value | Description |
|-----------------|-------|-------------|
| User            | `0`   | Userspace. |
| Kernel          | `1`   | Kernelspace. |
| Secure Monitor  | `2`   | Above the kernel, meant for software kernel secure mechanisms like Apples PPL. |

A core comes out of reset in the secure monitor level. Elevation can only be dropped by writing `crel`, writing a higher level than the current one raises a permission exception. The way back up is a trap or a interrupt.

## Opcode Set
(1) Applies a mathematical operation on two values and stores the result into the first operand, which must always be a register. With two operands that is `dst = dst op b`, with three operands it is `dst = a op b`, so the destination doesn't have to be one of the sources.

(2) Variadic instruction, meaning it can be used to apply the same operation onto many registers at the same time.

In the operand column `[x]` is a optional operand. `addr` is a value that is used as a memory address and `target` is a branch target.

### Core
| Opcode | Binary | Operands | Description |
|--------|--------|----------|-------------|
| `hlt` | `0b00000000` |  | Halts the core until the next interrupt comes in from a timer or a other device. |
| `nop` | `0b00000001` |  | Does nothing, does a cycle. |

### v19, binary size reduction
| Opcode | Binary | Operands | Description |

## The stack and calls
The stack grows downwards and `sp` points to the next free quad word, not to the last used one.

- `push` stores the value at `sp` and then subtracts 8 from `sp`.
- `pop` adds 8 to `sp` and then loads the value from there.

That means the first value of a stack you just set up lands at the address you put into `sp`, so a fresh `sp` is the top of your stack memory minus 8 and not the top it self.

`bl` pushes the return address, then pushes `fp`, and then sets `fp` to `sp`. So inside of a function that was called with `bl`:

| Address    | What lives there |
|------------|------------------|
| `fp + 16`  | The return address |
| `fp + 8`   | The `fp` of the caller |
| `fp` and below | Free for the function |

`ret` sets `sp` back to `fp`, pops `fp` and pops the return address into `pc`. That also means a function doesn't have to clean up its stack before it returns, `ret` throws everything away that was allocated below `fp`.

`blw` is the wasteful brother. It pushes the return address, `fp`, `cf`, `fpc` and `r0` - `r9`, which is 14 quad words, then puts the operands behind the target into `r0` and upwards and branches. `wret` restores all of it, which is why `rr` is the way to return a value from a `blw` call. It is simple and it is expensive, compilers use `bl`.

## Exceptions
| Exception        | Value | Description |
|------------------|-------|-------------|
| None             | `0`   | Normal state, nothing to see. |
| Bad Access       | `1`   | A memory address was accessed inappropriately, like outside of the physical memory or MMIO done wrong. |
| Permission       | `2`   | The current elevation did not have the permission to do that, like writing a control register from userspace. |
| Bad Instruction  | `3`   | The CPU tried to decode something that is not a valid instruction. |
| Bad Arithmetic   | `4`   | The ALU was asked to do illegal math, like N / 0 or N % 0. |
| Page Fault       | `5`   | The MMU found a page that is not mapped or not accessible in the way it was accessed. |
| KTRR Violation   | `6`   | Something tried to write into the locked kernel text region. |
| SVC              | `7`   | A system call. |
| PAC              | `8`   | `autia`, `autda` or `reta` found a pointer whose signature is wrong. |

How a exception gets delivered depends on the interrupt model the core is in.

## Trap model
The trap model is the modern way to take exceptions and interrupts and it is what Linux uses. It is turned on by setting the TRAPS bit in `crstat`.

| `crstat` bits | Name   | Meaning |
|---------------|--------|---------|
| 0             | IE     | Interrupts enabled. |
| 1             | PIE    | IE before the last trap. |
| 9 - 8         | PEL    | Elevation level before the last trap. |
| 16            | TRAPS  | Trap model enabled. |

All other bits read as zero. Writing a PEL that is higher than the current elevation raises a permission exception.

When a exception or a interrupt is taken the core does this:

1. PIE becomes IE, PEL becomes the current elevation level and IE gets cleared.
2. The elevation level is raised to kernel when it was user.
3. `crepc` becomes the address to return to, `crcause` what happened and `crtval` the faulting address.
4. `pc` becomes `crtvec`.

Nothing is pushed and no register is touched, saving them is the job of the handler and `crscratch` is there to help with that. There is only one entry for everything, the handler finds out what happened by reading `crcause`:

| `crcause` bits | Meaning |
|----------------|---------|
| 63             | Set when it was a interrupt. |
| 7 - 0          | The exception from the table above, or the interrupt line when bit 63 is set. |
| 15 - 8         | For memory faults the type of access, `1` read, `2` write, `3` execute. |

What `crepc` points to:

- For a exception, the instruction that caused it. Traps are precise, the faulting instruction leaves all registers as they were before it started, also the ones a "Register Increment" coding already changed. So after the kernel fixed the cause it can just `eret` and the instruction runs again.
- For `svc`, the instruction behind the `svc`.
- For a interrupt, the instruction that would have been executed next.

`eret` goes back: the elevation level becomes PEL, IE becomes PIE, PIE gets set, PEL gets cleared and `pc` becomes `crepc`. It needs kernel elevation and it raises a bad instruction exception when the trap model is off.

`wfe` only puts the core to sleep in the trap model.

## Legacy interrupt model
This is what a core does when the TRAPS bit is clear and what emexFirmware uses. Its the model from before v17.

The interrupt controller has a vector table, a array of quad words in memory where every entry is the address of the handler for one interrupt line. When a interrupt comes in, the core raises the elevation level to kernel, switches `sp` to `crksp` and pushes a frame of 16 quad words onto that stack, in this order:

1. the elevation level it had
2. the address to return to
3. the `sp` it had
4. `fp`, `cf`, `fpc`
5. `r0` - `r9`

Then `fp` is set to `sp` and `pc` to the handler address from the vector table. `iret` restores all of that and returns.

More things to know about it:

- Exceptions come in on interrupt line 0 and the exception number is in `crexc`. `svc` comes in on line 4.
- While a core is in a handler no other interrupt gets delivered to it.
- While a core is in a handler the MMU is bypassed, the handler runs on physical addresses.
- The extended and the floating point registers are not part of the frame.

## Memory
A address has 53 usable bits. Everything from bit 53 upwards is not memory:

| Addresses | What |
|-----------|------|
| `0x0000000000000000` - `0x001FFFFFFFFFFFFF` | Memory. Physical memory when the MMU is off, virtual memory when it is on. |
| `0x0020000000000000` - `0x003FFFFFFFFFFFFF` | MMIO. |
| everything above | Nothing, raises a bad access exception. |

MMIO sits above everything on purpose, that way it doesnt sit in the middle of the memory, which is better for page memory management on the OS side.

### MMU
The MMU translates with 4 levels of page tables and 8 KiB pages. A page table is one page big and holds 1024 entries of a quad word each.

| Virtual address bits | Used for |
|----------------------|----------|
| 52 - 43              | Index into the 1st level table |
| 42 - 33              | Index into the 2nd level table |
| 32 - 23              | Index into the 3rd level table |
| 22 - 13              | Index into the 4th level table |
| 12 - 0               | Offset inside of the page |

Every entry, on every level, looks the same:

| Bits     | Name     | Meaning |
|----------|----------|---------|
| 0        | Present  | The entry is valid. |
| 1        | User     | Userspace can access the page. |
| 2        | Dirty    | Set by the MMU when the page was written. |
| 3        | Read     | The page is readable. |
| 4        | Write    | The page is writable (most MMU's don't have that, but this one does). |
| 5        | Exec     | The CPU core can fetch instructions from the page and execute them. |
| 6        | Accessed | Set by the MMU when the page was accessed. |
| 7        | -        | Not used. |
| 63 - 8   | PFN      | The physical frame number, the physical address is the PFN shifted left by 13. |

On the first three levels only Present and the PFN matter, the PFN is the next table. The permission bits are only checked on the last level. Read, Write and Exec are three separate bits, so a page that can be executed but not read is a thing that works. A access from userspace additionally needs the User bit. The MMU sets Accessed and Dirty by it self, the kernel doesn't have to emulate them with faults.

`crptb` is the root of it all:

| `crptb` bits | Meaning |
|--------------|---------|
| 0            | Present, this turns the MMU on. |
| 47 - 8       | The PFN of the 1st level table. |
| 63 - 48      | The address space identifier (ASID). |

The TLB is tagged with the ASID, so switching to a other address space by writing `crptb` doesn't throw the translations of the old one away. When the kernel changes a page table entry it has to tell the TLB with `tlbi`. A translation that fails raises a page fault exception.

### MMIO
MMIO has rules, because the decoder later in actual emex64 hardware would explode in size otherwise. MMIO busses are complex!

- Every MMIO access has to be a quad word and aligned to a quad word boundary, so only `ldq` and `stq`. Anything else raises a bad access exception.
- MMIO is not translated by the MMU, MMIO addresses are used as they are and need no page table entries.
- Once the trap model or the MMU is on, MMIO needs kernel elevation.

### KTRR
The kernel text read-only region is a range of physical memory that the memory controller locks. After the lock two things are true, no matter what the page tables say:

- Nothing can write into the region anymore, on no elevation level.
- Code that runs with kernel elevation or higher can only be fetched from inside of the region. So a attacker that got data into kernel memory can't make the kernel execute it.

A attempt at either one raises a KTRR violation exception. The region can not be unlocked or moved again until the next reset. Linux locks its own text with it right before it starts the first process.

## Pointer authentication (PAC)
PAC is the `e` in emex64e. A pointer gets a signature put into its unused upper bits and the signature gets checked before the pointer is used, so a attacker that can overwrite a pointer in memory still can't make the CPU follow it.

- The signature lives in bits 63 - 54 of the pointer, that are 10 bit. Those bits are free since a address only has 53 usable bits and bit 53 is MMIO.
- The signature is a keyed hash (SipHash) over the pointer and a modifier. The modifier is a second value you choose, like the address where the pointer is stored, so the same pointer signed for a other place doesn't validate.
- There are two keys, `criakey` for instruction pointers and `crdakey` for data pointers.
- `crpac` turns it on, bit 0 for user code and bit 1 for kernel code.

When PAC is off for the current elevation level `pacia`, `autia`, `pacda`, `autda` and `pacret` do nothing and `reta` is just a `ret`. That way the same binary runs on both, with and without it.

When a check fails the register stays as it was, the core raises a PAC exception and `crtval` holds the pointer that failed.

For return addresses there is `pacret` and `reta`. A function does `pacret` right after it was called, that signs the return address in its frame with `fp` as the modifier, and returns with `reta` instead of `ret`.

## Floating point unit (FPU)
The FPU does IEEE 754 doubles and singles on the floating point register file. Instructions without a suffix work on doubles and the ones that end with `s` work on singles.

`fpc` controls it:

| `fpc` bits | Meaning |
|------------|---------|
| 1 - 0      | Rounding mode, `0` to nearest with ties to even, `1` toward zero, `2` toward negative infinity, `3` toward positive infinity. |
| 4          | NV, invalid operation. |
| 5          | DZ, division by zero. |
| 6          | OF, overflow. |
| 7          | UF, underflow. |
| 8          | NX, inexact. |

The flags are accrued, the FPU only sets them and software clears them. The FPU never raises a exception, a division by zero gives you infinity and the DZ flag.

Converting a float into a integer rounds toward zero and saturates. A value that is too big gives the biggest integer, a value that is too small the smallest one and a NaN gives zero, and all three set the NV flag. No garbage like on other architectures.

## Atomics
`xchg`, `cas`, `ldadd`, `ldand`, `ldor`, `ldxor` and `swpadd` read, modify and write memory as one step that no other core can get in between of. The address has to be aligned to the size of the access for that, 8 bytes for the normal ones and 4 bytes for the ones that end with `d`. On a address that is not aligned the instruction still does its work, but then it is a load and a store and not atomic anymore.

There is no load-linked/store-conditional kind of thing in emex64, `cas` does that job.

For waiting there is `wfe` and `sev`. `sev` sets a event on every core, `wfe` takes the event when there is one and sleeps until there is one when there is none. `pause` is for the short spin before you go to sleep.

## Reset
A core comes out of reset like this:

- `pc` is 0, so the firmware image has to be at the physical address 0.
- The elevation level is secure monitor.
- The MMU is off, the trap model is off and the active ISA version is the newest one.

Only the first core starts running by it self. The other cores wait until a running core sends them a startup interrupt through its local APIC, with the address they shall start at.

## Calling convention
This is what clang (`llvm/`) does. The CPU doesn't care, but your assembly should when it wants to talk to C.

| What                         | Where |
|------------------------------|-------|
| Integer and pointer arguments | `r0` - `r5`, the rest on the stack |
| Floating point arguments     | `fr0` - `fr7`, the rest on the stack |
| Variadic arguments           | All on the stack |
| Return value                 | `rr`, a second one in `r0` |
| Floating point return value  | `fr0`, a second one in `fr1` |
| Saved by the callee          | `r6` - `r9`, `er8` - `er14`, `fr8` - `fr15` |
| Saved by the caller          | Everything else |

Arguments that are smaller than 64 bit get extended to 64 bit, and every stack slot is a quad word. Calls are done with `bl` and `ret` (`pacret` and `reta` on emex64e).

## Object format
emex64 uses ELF, 64 bit and little endian, with the machine number `0x0E64`. ELF is the only thing that I didn't do from scratch, I originally wanted to use the LO(LightweightObject) format made by me, but thought then that this will be nightmares to implement.

The relocations you will meet the most:

| Relocation             | Value | Description |
|------------------------|-------|-------------|
| `R_EMEX64_NONE`        | `0`   | Nothing. |
| `R_EMEX64_ABS64`       | `1`   | The 64 bit address of the symbol. This is what the address coding is for. |
| `R_EMEX64_ABS32`       | `2`   | The low 32 bit of the address of the symbol. |
| `R_EMEX64_PC64`        | `5`   | The 64 bit distance from the place to the symbol. |
| `R_EMEX64_PC32`        | `6`   | The 32 bit distance from the place to the symbol. |
| `R_EMEX64_BRANCH32`    | `17`  | A 32 bit branch displacement that starts at bit 0 of the place. |
| `R_EMEX64_BRANCH32_B4` | `18`  | A 32 bit branch displacement that starts at bit 4 of the place, since operands are not aligned to a byte boundary. |
| `R_EMEX64_PLT32`       | `19`  | Like `R_EMEX64_BRANCH32`, for calls. |
| `R_EMEX64_PLT32_B4`    | `20`  | Like `R_EMEX64_BRANCH32_B4`, for calls. |

A branch with a 32 bit displacement reaches 2 GiB in both directions. Everything that is further away needs the 64 bit address coding.
